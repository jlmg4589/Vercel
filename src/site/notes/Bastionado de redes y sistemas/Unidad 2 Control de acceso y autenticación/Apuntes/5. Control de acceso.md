# 5. Control de acceso

## 5.1 Concepto y objetivos

Históricamente el control de acceso fue un problema **físico** (murallas, fosos, puentes levadizos, puertas y llaves): solo quien tenía la llave adecuada accedía al recurso.

En informática, el **control de acceso** gestiona el acceso a los recursos protegidos y **determina si un usuario está autorizado** a acceder a un recurso concreto. Por ejemplo, una aplicación web tiene recursos para usuarios autenticados, recursos solo para administradores y recursos públicos.

- Comprende mecanismos de **autenticación, autorización y auditoría** (ver [[Bastionado de redes y sistemas/Unidad 2 Control de acceso y autenticación/Apuntes/2. Seguridad activa#2.1.2 AAA (Authentication, Authorization and Accounting)\|AAA]]).
- **Objetivos:** proteger datos y recursos frente al **acceso no autorizado** (secreto/confidencialidad) y la **modificación no autorizada** (integridad), garantizando a la vez el acceso de los usuarios legítimos (**no denegación de servicio**).
- Además permite garantizar:
  - Que solo las personas autorizadas acceden a sistemas, equipos, programas o aplicaciones.
  - Que se **identifican y auditan** los accesos, con controles internos.
  - Que se **documentan** los procedimientos de acceso a aplicaciones que tratan **datos personales**.

> [!warning] Escalada de privilegios
> Los ataques de **escalada de privilegios** buscan acceder a recursos que no deberían estar disponibles para un usuario. Debe existir una **política específica** con mecanismos para impedirlos.

## 5.2 Requisitos de un sistema de control de acceso

Un sistema de control de acceso es un **mecanismo de monitorización** que intercepta **todas** las peticiones de recursos. Debe ser:

- **Resistente a manipulaciones:** no puede alterarse y, si se altera, debe detectarse.
- **No eludible:** todo acceso debe pasar por él; si se puede saltar, habrá peticiones sin analizar.
- **Con seguridad nuclear:** la seguridad se concentra en un **núcleo**, no distribuida por todo el sistema (evita validar todo el código en cada punto de acceso).
- **De tamaño pequeño:** para permitir la **prueba formal** de su seguridad.

## 5.3 Fases del desarrollo de un sistema de control de acceso

1. **Definición de políticas de seguridad:** reglas en **lenguaje natural**, abstractas y a veces vagas o ambiguas (hacen referencia a leyes, procesos o procedimientos). Ej.: "Todos los ingenieros de *nivel avanzado* tienen acceso al ordenador central" (*nivel avanzado* deberá formalizarse).
2. **Representación del modelo formal de seguridad:** se representan formalmente las reglas, lo que permite **demostrar** que el sistema cumple determinadas propiedades.
3. **Desarrollo de los mecanismos de seguridad:** implementación con lenguajes de programación interpretados de forma **determinista y sin ambigüedad**.

## 5.4 Políticas de acceso

Todo sistema de control de acceso considera tres elementos:

- **Objetos (objetivos):** entidades a proteger. En un SO: archivos, directorios, programas, dispositivos, terminales, puertos… En una BD: tablas, relaciones, vistas, procedimientos…
- **Acciones:** lo que se hace sobre un objeto: lectura, escritura, creación, eliminación y, en programas, ejecución.
- **Sujetos (iniciadores):** entidades que solicitan acceso: **usuarios** y **procesos** (navegador, procesador de textos…).

Los sujetos realizan acciones sobre objetos, y el sistema decide si las permite según las **políticas de acceso**. Hay tres tipos fundamentales:

| Tipo | Quién gestiona las políticas | Uso típico |
| --- | --- | --- |
| **Centralizado / obligatorio (MAC)** | El sistema, como ente central; los sujetos no pueden redefinirlas | Entornos militares, clasificación por niveles |
| **Discrecional (DAC)** | Los **propietarios** de los objetos, que pueden ceder permisos | Sistemas operativos |
| **Basado en roles (RBAC)** | El sistema, mediante permisos de **rol** | Bases de datos, grandes organizaciones |

> Busca la política de seguridad sobre contraseñas del marco de desarrollo de la Junta de Andalucía (**MADEJA**) y resume sus requisitos.

### 5.4.1 Control de acceso centralizado (obligatorio)

Las políticas las evalúa una **autoridad central** (en un SO, el núcleo). Se usan sistemas **multinivel**: sujetos y objetos tienen una **clase de acceso** y, para acceder a un objeto, el sujeto debe tener una clase **igual o superior**. Se inspira en el ámbito militar (unos planes de ataque solo los ve quien tiene nivel de coronel).

Cada clase de acceso tiene dos componentes:

- **Nivel de seguridad (N):** elemento de un conjunto **jerárquico ordenado** (p. ej. SA > SM > SB).
- **Conjunto de categorías (C):** subconjunto de un conjunto **no ordenado** de áreas funcionales (gestión, investigación, transferencia, docencia…).

**Relación de dominancia:** c1 domina a c2 si su nivel es mayor o igual y su conjunto de categorías incluye al de c2:

$$\forall c_1=(N_1,C_1),\ c_2=(N_2,C_2):\ c_1 \geq c_2 \Leftrightarrow N_1 \geq N_2 \wedge C_1 \supseteq C_2$$

Cumple las propiedades reflexiva, transitiva, antisimétrica y de existencia de cotas superior e inferior. El **control de acceso obligatorio** restringe el acceso según la **sensibilidad** de la información y la **autorización formal** (*clearance*) del sujeto.

### 5.4.2 Control de acceso discrecional (DAC)

Definido en el ***Trusted Computer System Evaluation Criteria*** (1985). Se basa en **quién** pide el acceso y en reglas explícitas definidas por los **propietarios (*owners*)** de los objetos. Es "discrecional" porque los usuarios pueden **transferir sus privilegios** a otros; al no haber una autoridad única, son necesarias **políticas de administración**.

#### 5.4.2.1 Matriz de acceso

Cada celda **M(i,j)** contiene las acciones que el sujeto *i* puede realizar sobre el objeto *j*. Como con muchos sujetos y objetos la mayoría de celdas quedan vacías, se usan **tablas de autorización** de tres columnas (**sujeto, acción, objeto**) con solo las celdas no vacías.

#### 5.4.2.2 Listas de control de acceso (ACL)

El administrador define **grupos** (un grupo es un nombre que define un rol) y asigna permisos sobre los recursos a usuarios y grupos. Los SO traen grupos predefinidos ("Todos los usuarios", "Administradores", "Usuarios del dominio", "Usuarios autentificados"…) y un usuario puede pertenecer a varios.

> [!tip] Buena práctica
> **No asignar permisos a usuarios directamente, sino siempre a grupos**, aunque el grupo tenga un solo usuario.

La ACL se almacena junto al fichero o carpeta como **metadatos** (como su nombre, fechas o tamaño). Los permisos dependen del tipo de recurso y, en ficheros, del **sistema de ficheros**:

- **NTFS (Windows):**
  - **Básicos:** lectura, modificación, lectura y ejecución, control total.
  - **Avanzados:** lectura (abrir carpeta, leer, ver atributos y permisos), escritura (crear, escribir, anexar, escribir atributos, eliminar), lectura y ejecución, administración (tomar posesión, cambiar permisos) y control total.
- **EXT4 (Linux):** solo **rwx** para **propietario, grupo y otros** (UGO), más permisos especiales. Para lograr la granularidad de Windows habría que crear muchos grupos, lo que es difícil de mantener; por eso Linux permite **ACL** montando el sistema de ficheros con `acl` y `user_xattr` y usando `getfacl`/`setfacl` (ver [[Bastionado de redes y sistemas/Unidad 2 Control de acceso y autenticación/Apuntes/5. Control de acceso#5.6 ACL y atributos en Linux\|#5.6 ACL y atributos en Linux]]).
- Red Hat con **SELinux** y SUSE con **AppArmor** ofrecen un modelo de permisos aún más avanzado (ver [[Bastionado de redes y sistemas/Unidad 7 Configuración de sistemas informáticos/Apuntes/3. Hardening de procesos\|3. Hardening de procesos]]).

### 5.4.3 Control de acceso basado en roles (RBAC)

En organizaciones grandes no es práctico definir privilegios uno a uno. En RBAC los permisos se asignan a **roles** y cada sujeto tiene un rol, adquiriendo sus privilegios. La gestión se simplifica: basta con **asignar bien los roles**. Es tan flexible que MAC y DAC pueden considerarse **casos particulares** de RBAC.

## 5.5 Permisos en Linux

### 5.5.1 Propietario y grupo

```bash
chown usuario:grupo elemento     # cambia usuario y grupo (-R recursivo)
chgrp grupo elemento             # cambia solo el grupo
```

### 5.5.2 Cambiar permisos con `chmod`

Conjuntos: **u** (usuario), **g** (grupo), **o** (otros), **a** (todos). Tres formas:

- **`+` y `-`:** la más concreta, solo afecta al permiso indicado.
- **`=`:** fija un conjunto entero de permisos.
- **Numérica (octal):** cambia **todos** los permisos. Cada permiso es un bit (r=4, w=2, x=1) agrupado de tres en tres.

```bash
chmod u+w-x,g-r,o+w carta.txt
chmod a+x script.sh
chmod u=rw,g=r,o-x directorio
chmod 640 fichero      # rw- r-- ---  (110 100 000)
```

> [!warning] Errata de la fuente
> El tutorial da como ejemplo `rw- r-- ---` = "110 010 000" = `602`. Lo correcto es **110 100 000 = 640**.

### 5.5.3 Permisos especiales

| Permiso | Efecto | Representación |
| --- | --- | :-: |
| **SetUID** | El programa se ejecuta con los permisos del **propietario** del fichero, no de quien lo invoca. Útil pero peligroso. | `s` en ejecución de usuario (4000) |
| **SetGID** | Igual con los permisos del **grupo**. En un directorio, lo creado dentro hereda el grupo del directorio. | `s` en ejecución de grupo (2000) |
| **Sticky bit** | En un directorio, los ficheros solo pueden ser **borrados/renombrados por su propietario** (o root). | `t` en ejecución de otros (1000) |

```bash
chmod u+s tux.sh
chmod 1777 /home/tmp/          # dígito extra: setuid, setgid, sticky
find / -type d -perm -002      # directorios escribibles por todos
find / -perm /6000             # ficheros con SUID o SGID
```

## 5.6 ACL y atributos en Linux

### 5.6.1 ACL

Ofrecen permisos adicionales y más flexibles: permisos **independientes para cualquier usuario o grupo** sobre el mismo recurso.

```bash
grep ACL /boot/config-$(uname -r)                    # soporte en el kernel
tune2fs -l /dev/sda1 | grep 'Default mount options:' # soporte en el FS

getfacl carta.txt                                    # ver la ACL
setfacl -m u:ana:r-x carta.txt                       # -m modificar
setfacl -Rm group:profesores:rw /home/profesores/    # -R recursivo
setfacl -x u:ana carta.txt                           # -x eliminar una entrada
setfacl -b carta.txt                                 # -b eliminar toda la ACL
setfacl -d -m g:profesores:rw /home/profesores/      # -d ACL por defecto (herencia)
setfacl -m m::r foto.jpg                             # máscara
```

- Un `+` al final de los permisos en `ls -l` indica que el elemento tiene ACL.
- La **máscara** define el **límite más permisivo** de cualquier entrada de la ACL y **siempre tiene preferencia**.

### 5.6.2 Atributos

Marcas del sistema de ficheros que modifican el comportamiento del elemento:

| Atributo | Significado |
| :-: | --- |
| `i` | Inmutable: no se puede modificar aunque tenga permiso de escritura |
| `a` | Solo añadir datos (útil para **logs**) |
| `A` | No actualiza la fecha de último acceso |
| `s` | Borrado seguro de los datos en disco |
| `u` | Al borrar, los datos se conservan en disco |
| `e` | Usa *extents* (menos fragmentación; por defecto en FS modernos) |

```bash
lsattr -R -a -d ruta                         # listar (recursivo, ocultos, directorio)
chattr -R +i /home/alumno/datos_privados/    # añadir con +
chattr -iA documento.doc                     # quitar con -
```

## 5.7 Configuración del acceso remoto

### 5.7.1 Configuración de terminales

El acceso por usuario/contraseña es vulnerable al ***sniffing*** y a la adivinación de contraseñas débiles, por lo que debe limitarse a lo operativamente necesario.

- En accesos locales, delimitar **por qué terminales se permite entrar como root** editando `/etc/securetty`.
- Establecer un **tiempo de expiración por inactividad** con la variable `TMOUT` (en `.bash_profile` o `.bashrc`), en **solo lectura** para que el usuario no la cambie:

```bash
TMOUT=120
readonly TMOUT
```

### 5.7.2 Configuración del acceso SSH

SSH es la forma habitual de administrar Linux en remoto; es más seguro que sus predecesores (rsh, telnet) pero requiere configuración. En `/etc/ssh/sshd_config`:

```bash
Protocol 2                 # solo la versión 2 (obsoleta en OpenSSH ≥ 7.4: ya solo existe SSH-2)
AllowUsers USER1 USER2     # lista blanca de usuarios (o DenyUsers USER1 USER2)
ClientAliveInterval 300    # segundos entre comprobaciones de inactividad
ClientAliveCountMax 0      # nº de comprobaciones antes de cerrar la sesión
IgnoreRhosts yes           # deshabilita los .rhosts (confianza entre máquinas UNIX)
PermitRootLogin no         # root no entra directamente en remoto
PermitEmptyPasswords no    # sin contraseñas vacías
Banner /etc/issue          # aviso legal al conectar
PermitUserEnvironment no   # el usuario no puede fijar variables de entorno
PasswordAuthentication no  # solo acceso con clave pública
```

**Autenticación por clave pública ("certificado"):**

```bash
ssh-keygen -f /home/frederic/id_rsa -t rsa -b 4096   # genera id_rsa e id_rsa.pub (pide passphrase)
ssh-copy-id -i /home/frederic/id_rsa.pub frederic@servidor   # copia a ~/.ssh/authorized_keys
ssh -i id_rsa frederic@192.168.0.120 -p 220          # conexión con la clave
```

Tras copiar la clave, el servidor pide la ***passphrase*** de la clave privada en lugar de la contraseña. El funcionamiento criptográfico de SSH (claves de *host*, ficheros de claves, `ssh-agent`) se explica en [[Bastionado de redes y sistemas/Unidad 3 Administración de credenciales de acceso/Apuntes/3. Infraestructuras de clave pública (PKI)#3.9 Certificados y claves para el acceso a un servidor remoto (SSH)\|Certificados y claves para el acceso SSH]] (UD3) y se practica en [[Bastionado de redes y sistemas/Unidad 3 Administración de credenciales de acceso/Prácticas/P1 - UD3 Acceso a un servidor remoto mediante claves SSH\|P1 - UD3 Acceso a un servidor remoto mediante claves SSH]]. Ver también [[Bastionado de redes y sistemas/Unidad 7 Configuración de sistemas informáticos/Apuntes/5. Securización de la administración remota\|5. Securización de la administración remota]] (UD7).

> [!info] Actualización 2026
> OpenSSH quitó el soporte de SSH-1 en la versión 7.4 (2016), así que la directiva `Protocol` ya no tiene efecto. Hoy se recomiendan claves **Ed25519** (`ssh-keygen -t ed25519`) o RSA de al menos 3072 bits. **DSA** se eliminó en OpenSSH 10.0 (2025) (actualizado, fuente: [OpenSSH Release Notes](https://www.openssh.org/releasenotes.html)).

## 5.8 Administración local

Aunque se preste mucha atención a los atacantes remotos, si alguien burla la seguridad perimetral y llega a la máquina, **no todo está perdido** si se ha reforzado la **seguridad local**. Hay que proteger el sistema localmente antes de exponerlo.

### 5.8.1 Cuentas de usuario

Tras instalar el sistema o programas se crean cuentas en `/etc/passwd` para aplicaciones concretas que un atacante podría aprovechar.

- Revisar `/etc/passwd` y **comentar/eliminar las cuentas innecesarias**.
- Las cuentas que no son de persona **no deben tener shell**: `/sbin/nologin` o `/bin/false`.
- Para valorar si una cuenta es necesaria: comprobar si es **propietaria de archivos** y su última fecha de modificación.
- Suelen ser necesarias: `root, bin, daemon, halt, shutdown, man, at`.
- Suelen sobrar en un sistema bastionado: `uucp, games, gdm, xfs, rpcuser, rpc`.

En Windows: la cuenta **Administrador** debe quedar **deshabilitada** (y con contraseña fuerte; puede renombrarse, aunque su SID termina en **-500**), **Invitado** deshabilitada, y el usuario inicial no debe usarse a diario (usar "Ejecutar como administrador"). Hay que vigilar el grupo **Administradores** y evitar **Usuarios avanzados**.

### 5.8.2 Ficheros de usuarios y contraseñas en Linux

**`/etc/passwd`** – usuarios del sistema:

```text
usuario:x:UID:GID:datos_personales:directorio_home:shell
```

- `x`: la contraseña está en `/etc/shadow`.
- **UID 0** = root. Usuarios de sistema: 1–499 (Red Hat) o 1–999 (Debian).

**`/etc/shadow`** – contraseñas cifradas y su validez:

```text
alumno:$6$CmR8XmO6$/Cbjq...:17802:0:99999:7:::
```

1. Usuario.
2. Contraseña con formato `$id$salt$hash`: `$1$` MD5, `$2a$`/`$2y$` Blowfish, `$5$` SHA-256, `$6$` SHA-512. El ***salt*** añade dígitos aleatorios antes del *hash* y dificulta los ataques. `!` o `*` impiden el acceso por contraseña; un `!` inicial indica **cuenta bloqueada**; vacío = sin contraseña.
3. Último cambio (días desde 01/01/1970).
4. Días mínimos entre cambios.
5. Días máximos de validez.
6. Días de aviso antes de caducar.
7. Días desde la caducidad hasta deshabilitar la cuenta.
8. Fecha absoluta de caducidad de la cuenta.

**`/etc/group`** – grupos y miembros secundarios: `alumnos:x:1002:juan,maria` (nombre, contraseña en *gshadow*, GID, miembros).

### 5.8.3 Comandos de gestión de usuarios

```bash
useradd -m -d /home/juan -g alumnos -G sudo -s /bin/bash -k /etc/skel juan
adduser juan                 # script interactivo
usermod / userdel -r juan    # modificar / borrar (con -r borra home y correo)
groupadd / groupmod / groupdel
passwd juan                  # cambiar contraseña; -l bloquea (añade !), -u desbloquea
chage -l juan                # ver validez; -d -E -I -m -M -W para cambiarla
getent passwd alumno         # consultar usuarios, grupos, etc.
```

`/etc/skel/` contiene la plantilla que se copia a los nuevos *home*.

### 5.8.4 Política de contraseñas y comprobaciones generales

Hay que **forzar** una política común (herramientas como `pwgen` generan contraseñas seguras, pero no bastan).

```bash
awk -F: '($2 == "") {print}' /etc/shadow   # cuentas sin contraseña (salida vacía)
awk -F: '($2 != "x") {print}' /etc/passwd  # hashes fuera de shadow (salida vacía)
awk -F: '($3 == "0") {print}' /etc/passwd  # cuentas con UID 0 (solo root)
```

**Caducidad y parámetros en `/etc/login.defs`:**

| Directiva | Función |
| --- | --- |
| `PASS_MAX_DAYS` / `PASS_MIN_DAYS` | Días máximos de validez / mínimos entre cambios |
| `PASS_WARN_AGE` | Días de aviso antes de caducar |
| `PASS_MIN_LEN` / `PASS_MAX_LEN` | Longitud mínima / máxima |
| `ENCRYPT_METHOD` | Algoritmo de *hash* (SHA512 por defecto) |
| `LOGIN_RETRIES` / `LOGIN_TIMEOUT` | Intentos de login y tiempo máximo |
| `UID_MIN`/`UID_MAX`, `GID_MIN`/`GID_MAX` | Rangos de IDs de nuevos usuarios/grupos |
| `UMASK` | Máscara para los nuevos *home* (022 por defecto; **077** más seguro) |
| `DEFAULT_HOME` | Si se puede entrar sin acceso al *home* |

```bash
PASS_MAX_DAYS 60
PASS_MIN_DAYS 7
PASS_MIN_LEN 10
PASS_WARN_AGE 7
```

Para un usuario concreto:

```bash
chage -M <DÍAS_MAX> -m <DÍAS_MIN> -W <DÍAS_AVISO> <usuario>
```

> [!note]
> Varias directivas de `login.defs` han sido sustituidas por **PAM** (complejidad, bloqueo, histórico): ver [[Bastionado de redes y sistemas/Unidad 2 Control de acceso y autenticación/Apuntes/7. Pluggable Authentication Modules (PAM)\|7. Pluggable Authentication Modules (PAM)]]. En Windows se usan las **directivas de contraseñas y de bloqueo de cuenta** (GPO o PSO en dominio).

**Contraseñas débiles:** auditar periódicamente con **John the Ripper** (o MBSA en Windows).

### 5.8.5 Privilegios y límites

- **`sudo`**: ejecuta órdenes como administrador. Se configura con `visudo` (comprueba la sintaxis) en `/etc/sudoers`: `usuario host=(usuario:grupo) comandos`, con alias y `ALL`.
- **`su -`**: cambia de usuario (root por defecto) cargando su entorno.
- **`who`, `w`, `last`**: quién está conectado y últimos accesos.
- **`/etc/security/limits.conf`**: límites por usuario/grupo con formato `domain type(hard|soft) item value`; `ulimit` para el sistema.
