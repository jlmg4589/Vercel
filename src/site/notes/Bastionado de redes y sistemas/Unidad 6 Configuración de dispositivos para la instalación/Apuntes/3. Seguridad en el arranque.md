# 3. Seguridad en el arranque

El **proceso de arranque** es un momento crítico: si no se toman precauciones, un actor malintencionado puede tomar el control del sistema de forma **silenciosa y transparente** para el sistema operativo.

Todas las estaciones de trabajo disponen de un sistema básico de arranque grabado en memoria de solo lectura (normalmente una EPROM actualizable) llamado **firmware**. Se encarga de **inicializar el hardware**, cargar el sistema operativo (o un gestor de arranque más complejo) y ejecutarlo.

- En PC Intel/compatibles: **BIOS** o, actualmente, **UEFI**.
- En estaciones SPARC (y antiguos PowerPC de Apple): **OpenBoot**, implementación del estándar **IEEE 1275-1994**.

> [!note]
> En general, las protecciones configuradas en el firmware pueden evitarse **desmontando el equipo**, pero en un entorno de trabajo normal suelen ser suficientes.

## 3.1 Mecanismos de arranque: BIOS y UEFI

- **BIOS** (*Basic Input/Output System*): firmware estándar para verificar e inicializar el hardware y gestionar el arranque. Es un sistema de **16 bits** con limitaciones de seguridad (**código no firmado** y arranque en **modo real** de la CPU) y de tamaño de discos/particiones. Aparece en 1975 (CP/M). Los fabricantes más conocidos son **Phoenix** y **AMI**.
- **UEFI** (*Unified Extensible Firmware Interface*): nace para relevar a BIOS, superando la limitación de particiones y mejorando la seguridad del arranque. EFI nace en 1998; la especificación UEFI, en 2005; Apple la adopta en 2006; desde 2011 la mayoría de PC la incorporan (a menudo con el módulo de compatibilidad **CSM**, que permite arrancar "al estilo BIOS") y desde 2012 todos los equipos con Windows 8.

### 3.1.1 BIOS frente a UEFI

| Aspecto | BIOS | UEFI |
| --- | --- | --- |
| Tabla de particiones | **MBR** (primer sector, 512 bytes; 16 bytes por entrada, máx. **4 primarias**) | **GPT**, hasta **128 particiones** (admite MBR por compatibilidad) |
| Direccionamiento | LBA de 32 bits → máx. 2^32 × 512 = **2 TB** | LBA de 64 bits → máx. 2^64 × 512 ≈ **9 ZB** |
| Integridad del código | Solo control **CRC**, sin firma | **Firma digital** del firmware y del código de arranque (**Secure Boot**) |
| Modo de CPU | **Modo real**: acceso total a memoria y hardware | **Modo protegido** con memoria virtual: restringe accesos arbitrarios |
| Cargador | Código en MBR/VBR | Ficheros PE en una **partición FAT32** especial (ESP) |

### 3.1.2 La BIOS del PC y la seguridad

Se accede pulsando una o varias teclas al arrancar; ofrece un entorno de configuración sencillo (fecha y hora, discos, controladoras…). Lo más relevante para la seguridad es la **elección de los dispositivos de arranque**: si se permite arrancar desde disquete o CD-ROM, cualquiera puede arrancar otro sistema y modificar nuestros ficheros.

Además de configurar el orden, hay que **limitar el acceso a la BIOS**. La mayoría ofrecen **dos contraseñas independientes**:

- **Contraseña de configuración (*setup*):** se pide tras pulsar la tecla de acceso a la BIOS.
- **Contraseña de arranque:** sin ella no se inicia el arranque. Inconveniente: hay que estar **delante del equipo**, poco práctico con reinicios remotos o cortes de luz.

La BIOS carga el sistema de forma muy simple: ejecuta el código del **MBR** o, si no hay, el del sector de arranque de la partición activa. No puede pasar parámetros al sistema ni elegir entre varios, por lo que en Linux se instala un *bootloader* como **LILO** o **GRUB**.

## 3.2 Secuencia de arranque

### 3.2.1 Arranque BIOS

1. Al encender se ejecuta el test de hardware (**POST**) y la BIOS se carga en memoria.
2. Busca el **primer dispositivo de arranque** según el orden configurado.
3. Lee el **MBR** (512 bytes): código inicial de arranque (fase 1, unos 400 bytes), parámetros del disco, tabla de particiones, firma del disco (32 bits) y el marcador final **0x55AA**.
4. El código del MBR salta a la **fase 2**: el *bootloader*, situado en el primer sector de la partición de arranque (**VBR**, *Volume Boot Record*), que gestiona el menú multisistema y carga el sistema operativo.

*Bootloaders* conocidos: **NTLDR** (Windows 2000/XP), **BOOTMGR** (Windows 7/8/10) y **GRUB2** (Linux).

### 3.2.2 Arranque UEFI

- No necesita código de un MBR/VBR: el código está **embebido en el firmware** (binarios y drivers en formato **PE**).
- El firmware tiene **variables** configurables para gestionar el arranque, accesibles con herramientas como `efibootmgr` (Linux), `bootcfg` (Windows) o `bless` (macOS). Por ejemplo, indican dónde está el *bootloader* en la partición FAT32.
- Usa el **modo protegido** de la CPU.
- Dispone de **Secure Boot**, que verifica criptográficamente *bootloaders*, drivers y variables UEFI antes de permitir el arranque.

```bash
# Consultar las entradas de arranque UEFI en Linux
efibootmgr -v
```

## 3.3 Bootkits

Un ***bootkit*** aprovecha el arranque para infectar el equipo **antes de que se inicie el sistema operativo**, evitando protecciones e inyectando código en el kernel; por eso su detección y eliminación es muy complicada.

- **Evolución:** el primer concepto de infección del arranque es **Brain** (1987, sector de arranque de disquete). En la BlackHat de 2005 la prueba de concepto **eEye** demostró la manipulación del MBR para infectar Windows.
- **Puntos de infección:** código de arranque del **MBR/VBR** en BIOS (fácil al no estar firmado), ficheros de arranque del kernel o *bootloaders*, drivers o, lo más intrusivo, el **firmware**.
- **Bootkits UEFI:** la mayoría ataca BIOS, pero pruebas como **Dreamboot** o *"Setup for Failure: Defeating Secure Boot"* (Syscan 2014) mostraron elementos de UEFI sin verificación estricta de firma (**Option ROM**, **drivers DXE**, *bootloader*).

MITRE ATT&CK recoge estas técnicas en **T1542.001 (Pre-OS Boot: System Firmware)**:

| ID | Nombre | Descripción |
| :-: | --- | --- |
| S0047 | Hacking Team UEFI Rootkit | Rootkit UEFI para persistir software de acceso remoto. |
| S0397 | LoJax | Rootkit UEFI; considerado el primero capaz de evadir Secure Boot (corregido en firmware posterior). |
| S0001 | Trojan.Mebromi | Modifica la BIOS, descarga y ejecuta ficheros y se protege de su eliminación. |

## 3.4 Configuración del arranque seguro

### 3.4.1 UEFI + Secure Boot

- **Migrar/sustituir** los equipos con arranque BIOS (mecanismo obsoleto) por equipos **UEFI**.
- **Habilitar Secure Boot**: verifica drivers, *bootloaders*, kernel y firmware apoyándose en claves criptográficas en ROM y, si existe, en el **TPM**.
- **Actualizar el firmware** según recomiende el fabricante, ya que surgen técnicas contra implementaciones antiguas de UEFI.

> [!tip]
> Algunas distribuciones Linux pueden no instalarse con Secure Boot activado; en ese caso hay que valorar el riesgo antes de desactivarlo.

> [!info] Actualización 2026
> - **Windows 11** exige como requisito mínimo firmware **UEFI con capacidad de Secure Boot** y **TPM 2.0** (actualizado, fuente: [Windows 11 specifications – Microsoft](https://www.microsoft.com/en-us/windows/windows-11-specifications)).
> - Las distribuciones principales (Debian, Ubuntu, Fedora…) arrancan con Secure Boot activo mediante el cargador firmado **shim**, por lo que rara vez es necesario desactivarlo (actualizado, fuente: [Debian Wiki – SecureBoot](https://wiki.debian.org/SecureBoot)).

### 3.4.2 Trusted Boot (arranque de confianza) en Windows

En Windows 8.1 y posteriores, el **arranque de confianza** continúa donde termina Secure Boot:

1. El cargador de arranque comprueba la **firma digital del kernel** de Windows.
2. El kernel comprueba el resto de componentes: controladores de arranque, archivos de inicio y el **ELAM** (*Early Launch Anti-Malware*), que comprueba los controladores de terceros.
3. Si un archivo se ha modificado, el cargador **se niega a cargarlo** y Windows puede repararlo automáticamente.

### 3.4.3 Seguridad en la OpenBoot PROM de Sun (SPARC)

El firmware de SPARC es una NVRAM llamada **OpenBoot PROM (OBP)**. Se accede con **Stop-A** (teclado Sun) o **Ctrl-Break** (terminal serie): se detienen todos los procesos y aparece el *prompt* `ok`. El problema es que cualquiera podría así rearrancar desde disco, CD-ROM o red y tomar el control. Soluciones: deshabilitar Stop-A con la directiva `abort_enable` en `/etc/system` o proteger la NVRAM con contraseña.

Niveles de seguridad (`security-mode`):

| Nivel | Comportamiento |
| :-: | --- |
| `none` | Por defecto, sin seguridad. |
| `command` | Pide clave para arrancar desde un dispositivo distinto del predeterminado. |
| `full` | Pide clave siempre (impide reinicios automáticos). |

```bash
eeprom security-mode            # consultar (security-mode=none)
eeprom security-mode=command    # activar command-secure (pide nueva contraseña)
eeprom security-password=       # cambiar la contraseña (nunca se muestra)
eeprom security-#badlogins=0    # resetear el contador de intentos fallidos
eeprom security-mode=none       # eliminar la protección
```

Desde el propio *prompt*: `ok setenv security-mode command`.

> [!warning]
> La contraseña de la OBP no tiene relación con la de *root*, aunque *root* puede modificar la NVRAM con `eeprom`. Si se pierde y no se puede arrancar, hay que **sustituir la NVRAM**. En Solaris para Intel, `eeprom` solo simula estos parámetros en `bootenv.rc` y no tienen efecto.
