# 5. Securización de la administración remota

## 5.1 Administración remota y protocolos

La **administración remota** es la funcionalidad de algunos programas que permite realizar acciones desde un equipo local para que se ejecuten en otro remoto; por ejemplo, el responsable de red puede revisar un servidor sin moverse de su escritorio.

Estos sistemas **están expuestos a la red externa o pública** y son objetivo habitual de atacantes, por lo que hay que dotarlos de la seguridad apropiada para garantizar la confidencialidad.

| Protocolo | Puerto | Características | Seguridad |
| :-: | :-: | --- | --- |
| **Telnet** | 23/TCP | Terminal remoto, muy usado en UNIX (1969). Útil aún para diagnosticar servidores de texto claro (HTTP, SMTP) | **Texto claro**: cualquier *sniffer* captura las credenciales. En desuso |
| **rsh / rlogin / rcp** | — | Órdenes remotas clásicas de UNIX | Sin cifrado; se sustituyen por SSH |
| **SSH** | 22/TCP | «Versión cifrada de Telnet»: además copia datos (scp, sftp) y crea túneles seguros | Cifrado con claves pública/privada |
| **VNC** | — | Acceso gráfico multiplataforma: envía teclado/ratón y recibe la pantalla | La seguridad inicialmente solo existe al principio de la comunicación |
| **RDP** | 3389/TCP | Escritorio remoto de Microsoft (*terminal services*), con compresión y cifrado propios | Cifra toda la información |
| **NFS** | 2049/TCP | Acceso remoto a ficheros en UNIX/Linux; la versión reciente soporta Kerberos, cortafuegos y ACL | Depende de la versión |
| **SMB** | 445/TCP | Acceso remoto a archivos e impresoras en Windows (compatible con Linux) | Depende de la versión |

Otros protocolos gráficos menos conocidos: **ICA** (*Independent Computing Architecture*, de Citrix) y **AIP** (*Adaptive Internet Protocol*, de Sun).

## 5.2 Herramientas RSAT en Windows 10

Las **RSAT** (*Remote Server Administration Tools*) son un kit de Microsoft para administrar equipos y servidores remotamente (Server Manager, MMC, cmdlets de PowerShell). Antes exclusivas de Windows Server, desde **Windows 10 October 2018 Update** cualquier usuario puede instalarlas.

### 5.2.1 Activar las RSAT

Vienen **deshabilitadas por defecto**. Se activan en:

**Configuración → Aplicaciones → Aplicaciones y características → Administrar funciones opcionales → Agregar una característica**

Aparecen 18 herramientas RSAT, cada una con su descripción.

### 5.2.2 Desinstalar las RSAT no necesarias

Las funciones instaladas son **persistentes** (sobreviven a las actualizaciones de Windows). Si no se usan, conviene desinstalarlas desde el mismo apartado (*Desinstalar*) para tener el sistema limpio de funciones innecesarias; desaparecen tras reiniciar.

## 5.3 Escritorio Remoto de Windows

Viene **desactivado por defecto** por seguridad y no está disponible en las ediciones *Home*. Si se habilita, **cualquiera con nuestra IP, usuario y contraseña podrá controlar el equipo**, por lo que antes hay que tener una contraseña segura.

Se accede buscando «Permitir el acceso remoto al equipo» o desde **Propiedades del PC → Configuración avanzada del sistema → Acceso remoto**. Allí aparecen *Asistencia remota* y *Escritorio remoto*:

1. Marcar «Permitir conexiones remotas a este equipo».
2. Pulsar **Seleccionar usuarios** y añadir solo los usuarios autorizados, para que una clave débil de otro usuario no ponga en peligro el sistema.
3. Probar la conexión desde otro equipo o un smartphone.

## 5.4 Pautas de securización

### 5.4.1 Securizar SSH

La configuración del **cliente** está en `/etc/ssh/ssh_config` y la del **servidor** en `/etc/ssh/sshd_config`. Tras cambiarla:

```bash
sudo systemctl restart ssh
```

#### 5.4.1.1 Directivas de seguridad del servidor

```text
# /etc/ssh/sshd_config
Port 5022                      # cambiar el 22 por otro poco evidente (no 2222)
Protocol 2                     # nunca admitir la versión 1
PermitRootLogin no             # entrar como usuario y elevar con su/sudo
AllowUsers manu itecma pepe    # o AllowGroups: solo usuarios/grupos concretos
MaxAuthTries 3                 # intentos antes de cortar la conexión
PasswordAuthentication no      # solo autenticación por clave pública
AuthorizedKeysFile .ssh/authorized_keys
X11Forwarding no               # sin túnel gráfico
AllowTcpForwarding no          # desactivar tunneling
AllowStreamLocalForwarding no
GatewayPorts no
PermitTunnel no
PrintLastLog no                # no mostrar el último login
PrintMotd no                   # no mostrar /etc/motd
```

- **Cambiar el puerto:** antes, comprobar los puertos en uso con `netstat -ntap` o `ss -ntap`. Después hay que indicar el puerto al conectar: `ssh -p 5022 usuario@equipo`.
- **Protocolo 2:** SSH v1 usa algoritmos patentados y es vulnerable a la inserción de datos en la comunicación. (En versiones modernas de OpenSSH la v1 ya no existe y la directiva está obsoleta — conocimiento general, verificar.)
- **Mensajes de bienvenida:** `PrintLastLog` y `PrintMotd` no desactivan el mensaje de la propia *shell*; para ello se usa `HUSHLOGIN_FILE` en `/etc/login.defs` o `touch ~/.hushlogin`, y conviene revisar las opciones *motd* de `/etc/pam.d/sshd`.

#### 5.4.1.2 Autenticación por clave pública

Es el método **más recomendable**, pero hay que proteger bien el equipo cliente: si roban la sesión de un equipo sin contraseña, podrían entrar en todas las máquinas a las que tenga acceso.

```bash
ssh-keygen -t rsa -b 4096                      # par de claves en ~/.ssh/
ssh-copy-id -i ~/.ssh/id_rsa.pub usuario@ip    # copia la pública a ~/.ssh/authorized_keys del servidor
```

- `-t` indica el algoritmo (rsa, dsa, ecdsa, ed25519…) y `-b` los bits.
- Ficheros de claves privadas:

| Cliente | Servidor |
| :-: | :-: |
| `~/.ssh/id_rsa` | `/etc/ssh/ssh_host_rsa_key` |
| `~/.ssh/id_dsa` | `/etc/ssh/ssh_host_dsa_key` |
| `~/.ssh/id_ecdsa` | `/etc/ssh/ssh_host_ecdsa_key` |
| `~/.ssh/id_ed25519` | `/etc/ssh/ssh_host_ed25519_key` |

Las públicas se llaman igual terminadas en `.pub`.

> [!note] Errata corregida
> Una fuente usa `ssh-keygen -t ecdsa -b 2084`; ECDSA solo admite 256, 384 o 521 bits (conocimiento general, verificar). La fuente de la UT7 escribe `-/.ssh/id_rsa.pub`; la ruta correcta es `~/.ssh/id_rsa.pub`.

#### 5.4.1.3 ssh-agent y túneles

- **`ssh-agent`** gestiona las claves privadas durante la sesión para no reautenticarse en cada servidor; las claves se añaden con `ssh-add`.
- **Túnel SSH:** conexión cifrada para transportar datos de otra aplicación.

```bash
ssh -N -f -L 8080:destino:80 usuario@origen
# -N no ejecuta comandos, -f segundo plano, -L puerto local:destino:puerto remoto
```

#### 5.4.1.4 Protección frente a fuerza bruta

- **DenyHosts** (Python): IPS de host para SSH que revisa los registros de autenticación y, al superarse los intentos fallidos desde una IP, la bloquea en una lista negra.
- **Fail2ban:** alternativa con características muy similares.
- **TCP Wrappers:** limitar desde qué hosts se acepta `sshd` (ver [[Bastionado de redes y sistemas/Unidad 7 Configuración de sistemas informáticos/Apuntes/2. Reducción del número de servicios#2.3.2 TCP Wrappers\|TCP Wrappers]]).

#### 5.4.1.5 Auditoría con ssh-audit

**ssh-audit** es una herramienta gratuita en Python que analiza la configuración del servidor SSH e indica, **con colores**, qué algoritmos son **seguros, débiles o inseguros**, para saber dónde intervenir.

```bash
ssh-audit ip_servidor
```

### 5.4.2 Securizar VNC

VNC tiene serios problemas de seguridad. Consta de **servidor** (en el equipo controlado) y **cliente**. Según un estudio de Kaspersky, prácticamente **todos los servidores VNC** tenían fallos graves: desde bloquear el servidor hasta **ejecutar código remoto**, capturar datos o tomar el control; muchos siguen sin corregir.

Recomendaciones:

- Revisar qué dispositivos pueden conectarse y, si es posible, usar una **lista blanca**.
- **Desactivar VNC** mientras no se use.
- Usar la **última versión** en cliente y servidor.
- **Contraseña segura**.
- No usar servidores que no sean de confianza.
- Si se necesita acceso remoto seguro, valorar una alternativa como RDP.

### 5.4.3 Securizar RDP

RDP es muy usado en empresas y también **objetivo frecuente de ciberdelincuentes**, especialmente para infectar con **ransomware**. Primero hay que valorar si es necesario; si no lo es, **deshabilitarlo**. Si es necesario:

- **Sistemas actualizados:** evitar sistemas sin soporte (Windows XP, Server 2008, Windows 7).
- **VPN:** situar una VPN entre usuario y servidor RDP. Es la opción con **más garantías**: doble barrera (VPN + escritorio remoto). Ver [[Bastionado de redes y sistemas/Unidad 5 Configuración de dispositivos y sistemas/Apuntes/11. VPN y túneles IPSec\|11. VPN y túneles IPSec]].
- **Usuarios no genéricos y contraseñas robustas** (evitar «Administrador»), tanto en la VPN como en RDP.
- **Bloqueo de cuenta** tras varios intentos fallidos, con tiempo de bloqueo creciente.
- **Doble factor de autenticación**, preferiblemente con aplicaciones específicas en lugar de SMS. Ver [[Bastionado de redes y sistemas/Unidad 2 Control de acceso y autenticación/Apuntes/3. Mecanismos y factores de autenticación\|3. Mecanismos y factores de autenticación]].
- **Cambiar el puerto 3389** si no se usa VPN (seguridad por oscuridad: dificulta ataques automatizados).
- **NLA** (*Network Level Authentication*): el usuario se autentica en la red antes que en el servidor RDP; limitar el acceso a los usuarios estrictamente necesarios y supervisar los accesos.
- **Reglas de cortafuegos** que solo permitan el acceso desde IP de equipos de la empresa.

### 5.4.4 Securizar NFS

NFS comparte sistemas de ficheros completos de forma muy transparente, lo que trae problemas de seguridad.

| Versión | Características |
| :-: | --- |
| NFSv2 | La más usada y soportada, pero **la más antigua e insegura** |
| NFSv3 | Más potente, no totalmente compatible con clientes v2. v2 y v3 funcionan sobre TCP o UDP |
| NFSv4 | **La más segura**: requiere **Kerberos** (KDC) configurado previamente; más compleja |

> [!tip] UDP en NFS
> UDP minimiza el tráfico, pero si el servidor cae los clientes siguen enviando mensajes y se satura la red.

Recomendaciones:

1. Usar los **comodines** lo menos posible (podríamos dar acceso a más equipos de los previstos).
2. Limitar con **iptables** el acceso a los puertos de los demonios NFS.
3. Configurar `/etc/hosts.allow` y `/etc/hosts.deny`.
4. Exportar en **solo lectura (`ro`)** siempre que sea posible.
5. Que el propietario de lo exportado sea root, ya que es posible mapear el UID de root al de *nobody*.
6. Evitar permiso de escritura para el grupo.
7. v2 y v3 **no controlan el acceso por usuario**: cualquier usuario de un cliente conectado accede; solo cabe exportar en lectura y reducir los usuarios a un UID/GID común.
8. Tener siempre activa alguna opción ***squash***: sin ella, el root del cliente obtiene acceso privilegiado con un simple `su -`.
9. Usar **NFSv4**.

```text
# /etc/exports (ejemplo, conocimiento general, verificar)
/srv/compartido  192.168.1.0/24(ro,root_squash,sync)
```

### 5.4.5 Securizar SMB

SMB permite acceder y modificar archivos e impresoras remotas entre equipos Windows y entre Windows y Linux. Pese a sus mejoras de cifrado y seguridad (última versión **SMB 3.1.1**, 2016), ha sido atacado; en particular Microsoft desaconseja el uso de la versión antigua **SMB1** (la fuente lo expresa de forma confusa; corrección basada en conocimiento general, verificar).

```powershell
# ¿SMB1 (CIFS) activo? Ver el campo State
Get-WindowsOptionalFeature -Online -FeatureName SMB1Protocol
# ¿SMB2/SMB3 activos? (el mismo parámetro cubre 2.x y 3.x)
Get-SmbServerConfiguration | Select EnableSMB2Protocol
# Desactivar SMB1 (en las versiones recientes de Windows 10 ya viene desactivado)
Disable-WindowsOptionalFeature -Online -FeatureName SMB1Protocol
# Desactivar SMB2/SMB3
Set-SmbServerConfiguration -EnableSMB2Protocol $false
```

Se recomienda reiniciar tras cada cambio.
