# 4. Eliminación de protocolos de red innecesarios

TCP/IP es un conjunto de protocolos que **no nació pensando en la seguridad**, por lo que conviene **deshabilitar todos los protocolos de red innecesarios** y limitar el uso de los demás al mínimo imprescindible. También es recomendable usar **NAT** para direccionar los equipos internos de una organización.

## 4.1 Protocolos de la capa de aplicación

Los protocolos de aplicación están **directamente asociados a los servicios instalados** en el servidor:

| Protocolo | Puerto | Servicio asociado (ejemplos) |
| :-: | :-: | :-: |
| SSH | 22 | ssh-server |
| DNS | 53 | bind9 |
| HTTPS | 443 | apache2, nginx |

Para eliminar estos protocolos basta con **deshabilitar o eliminar el servicio asociado**, como se vio en [[Bastionado de redes y sistemas/Unidad 7 Configuración de sistemas informáticos/Apuntes/2. Reducción del número de servicios\|2. Reducción del número de servicios]].

```bash
ss -tulpn                         # qué protocolos/puertos están a la escucha y qué proceso los ofrece
sudo systemctl disable --now apache2
```

## 4.2 Protocolos de otras capas (transporte, red…)

Para protocolos que no pertenecen a la capa de aplicación (por ejemplo **ICMP**, a nivel de red) se recomienda **filtrado de paquetes mediante *firewalls***, que permiten interceptar, analizar y manipular los paquetes. Un cortafuegos puede decidir usando cualquier parámetro TCP/IP: IP de origen o destino, puerto de destino (TCP o UDP), *flags* (RST, SYN, ACK…) o el propio protocolo, por ejemplo **«prohibir todos los paquetes ICMP»**.

> [!note] ICMP
> `ping` envía paquetes ICMP para comprobar si un destino responde. Responder a ICMP facilita a un atacante descubrir equipos activos (por ejemplo con `nmap -sP 192.168.0.0/24`), por eso suele filtrarse cuando no es necesario.

### 4.2.1 Filtrar ICMP con iptables / nftables

```bash
# iptables: descartar las peticiones de eco (ping) entrantes
iptables -A INPUT -p icmp --icmp-type echo-request -j DROP

# nftables: equivalente
nft add rule inet filter input icmp type echo-request drop
```

La sintaxis base procede de las fuentes (`iptables -t filter -A INPUT -p icmp -j ACCEPT`, `icmp type <tipo>` en nftables); las reglas concretas de descarte son adaptación. Bloquear **todo** ICMP rompe funciones necesarias (p. ej. *Path MTU Discovery*, mensajes *destination unreachable*); por eso se filtra solo `echo-request`. Ver [[Bastionado de redes y sistemas/Unidad 5 Configuración de dispositivos y sistemas/Apuntes/10. Configuración segura de cortafuegos, enrutadores y proxies\|10. Configuración segura de cortafuegos, enrutadores y proxies]].

### 4.2.2 Ignorar ICMP desde el kernel

Alternativa sin cortafuegos (actualizado, fuente: [Linux kernel docs – IP Sysctl](https://docs.kernel.org/networking/ip-sysctl.html)):

```bash
sudo sysctl -w net.ipv4.icmp_echo_ignore_all=1          # ignora todos los ECHO (ping)
sudo sysctl -w net.ipv4.icmp_echo_ignore_broadcasts=1   # ignora ECHO/TIMESTAMP a broadcast/multicast (ya es 1 por defecto)
# persistente: fichero en /etc/sysctl.d/ (p. ej. 99-icmp.conf) y 'sudo sysctl --system'
```

> [!info] Actualización 2026
> En distribuciones con systemd, la configuración persistente se coloca preferentemente en `/etc/sysctl.d/*.conf` (en algunas, como Debian 13, `/etc/sysctl.conf` ya no se lee por defecto). Fuentes: [sysctl.d(5)](https://man7.org/linux/man-pages/man5/sysctl.d.5.html), [Debian 13 release notes – /etc/sysctl.conf is no longer honored](https://www.debian.org/releases/trixie/release-notes/issues.en.html).

> [!info] Contenido complementario (fuente externa)
> Además de ICMP, conviene revisar en el propio host estos protocolos y opciones:
>
> 1. **Enrutamiento y redirecciones (Linux):** un equipo que no es *router* no debe reenviar paquetes, aceptar/enviar **redirecciones ICMP** ni aceptar **encaminamiento en origen** (*source routing*), que permiten a un atacante desviar el tráfico:
>
> ```bash
> # /etc/sysctl.d/99-hardening-red.conf  (aplicar con: sudo sysctl --system)
> net.ipv4.ip_forward = 0
> net.ipv4.conf.all.accept_redirects = 0
> net.ipv4.conf.all.send_redirects = 0
> net.ipv4.conf.all.accept_source_route = 0
> net.ipv6.conf.all.accept_redirects = 0
> net.ipv6.conf.all.accept_source_route = -1   # IPv6: <0 = no aceptar cabeceras de encaminamiento
> ```
>
> 2. **IPv6 si no se usa:** en Linux, `net.ipv6.conf.all.disable_ipv6 = 1` (y `default`) en el mismo fichero. En **Windows**, Microsoft **no recomienda desactivar IPv6** (algunos componentes dejan de funcionar); aconseja **preferir IPv4** (`DisabledComponents = 0x20`) o, como mucho, desactivar los **túneles** (6to4, ISATAP, Teredo) por GPO *Red > Configuración TCPIP > Tecnologías de transición IPv6*:
>
> ```powershell
> reg add "HKLM\SYSTEM\CurrentControlSet\Services\Tcpip6\Parameters" /v DisabledComponents /t REG_DWORD /d 0x20 /f
> Disable-NetAdapterBinding -Name "Ethernet" -ComponentID ms_tcpip6   # desvincular IPv6 de una interfaz (no recomendado sin necesidad)
> ```
>
> 3. **Resolución de nombres por multidifusión (LLMNR, mDNS) y NetBIOS:** responden a consultas de nombres en la red local y son objetivo de ataques de envenenamiento (*poisoning*) (conocimiento general, verificar).
>    - **Linux (systemd-resolved):** en `/etc/systemd/resolved.conf` poner `LLMNR=no` y `MulticastDNS=no`, y `sudo systemctl restart systemd-resolved`. Si está instalado **Avahi** (mDNS), `sudo systemctl disable --now avahi-daemon` (conocimiento general, verificar).
>    - **Windows – LLMNR:** GPO *Configuración del equipo > Plantillas administrativas > Red > Cliente DNS > **Desactivar resolución de nombres de multidifusión*** = Habilitada (valor `EnableMulticast = 0` en `HKLM\Software\Policies\Microsoft\Windows NT\DNSClient`).
>    - **Windows – NetBIOS sobre TCP/IP:** método WMI `SetTcpipNetbios` con valor **2 (DisableNetbios)**:
>
> ```powershell
> Get-CimInstance Win32_NetworkAdapterConfiguration -Filter "IPEnabled=true" |
>   Invoke-CimMethod -MethodName SetTcpipNetbios -Arguments @{TcpipNetbiosOptions=2}
> ```
>
> 4. **SMBv1:** ver [[Bastionado de redes y sistemas/Unidad 7 Configuración de sistemas informáticos/Apuntes/4. Eliminación de protocolos de red innecesarios#4.4 Desactivar protocolos de compartición en Windows: SMB\|apartado 4.4]].
> 5. **WPAD y SSDP/UPnP:** descubrimiento automático de proxy y de dispositivos; si no se usan, detener los servicios *WinHTTP Web Proxy Auto-Discovery* y *SSDP Discovery* en Windows, y no instalar/deshabilitar demonios UPnP en Linux (conocimiento general, verificar).
>
> Fuentes: [Linux kernel – IP Sysctl](https://docs.kernel.org/networking/ip-sysctl.html), [resolved.conf(5)](https://man7.org/linux/man-pages/man5/resolved.conf.5.html), [Microsoft Learn – Configure IPv6 for advanced users](https://learn.microsoft.com/en-us/troubleshoot/windows-server/networking/configure-ipv6-in-windows), [Microsoft Learn – ADMX_DnsClient (Turn off multicast name resolution)](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-admx-dnsclient), [Microsoft Learn – SetTcpipNetbios](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/settcpipnetbios-method-in-class-win32-networkadapterconfiguration).

## 4.3 Protocolos en dispositivos de red

Muchos protocolos vienen implementados en **dispositivos de red** (routers, switches). En situaciones extremas es posible **eliminarlos o desactivarlos desde su interfaz de administración**, por ejemplo **DHCP** o **IPv6**.

## 4.4 Desactivar protocolos de compartición en Windows: SMB

Ejemplo práctico de eliminación de protocolos es **SMB1**, versión antigua y vulnerable del protocolo de compartición de Windows (desarrollado en [[Bastionado de redes y sistemas/Unidad 7 Configuración de sistemas informáticos/Apuntes/5. Securización de la administración remota#5.4.5 Securizar SMB\|Securizar SMB]]):

```powershell
Get-WindowsOptionalFeature -Online -FeatureName SMB1Protocol     # ¿está activo SMB1?
Disable-WindowsOptionalFeature -Online -FeatureName SMB1Protocol # desactivarlo
```
